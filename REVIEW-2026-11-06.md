# Forge — code review and implementation, 6 November 2026

This is a second review. The package already contained `REVIEW.md` (an earlier
pass and its fixes: identifier/path validation, symlink-safe commits, dashboard
CSRF, shape-server rollback, mandatory model digests). That report was read
first. Its findings are not repeated here, and the fixes I re-checked by
reading still hold: `copy_outputs` refuses links, `safe_extract` writes regular
files only, IDs are validated before host writes, and commit refuses symlinked
destinations. Line numbers below refer to the **received** files.

## 1. Executive summary

**Overall health: 7/10.**
- **Strengths.** Explicit, code-driven orchestration. A real Docker sandbox
  (no network, read-only, capabilities dropped, non-root). Atomic state writes,
  run locks, and careful failure recovery. A large, meaningful test suite
  (533 + 68 + 43 tests, all green, fake servers rather than mocks of internals).
- **What holds the score down.**
  - Three places still trust model or generated output at a boundary: review
    verdicts, the size of `/out`, and the unattended `forge pending` timer.
  - `forge.py` is one 17,000-line module with per-run global state, which
    makes such boundaries hard to see.
- **Weaknesses found.** No Critical issues; three High:
  - One costs money without limit.
  - One spams the git host.
  - One can fill the host disk.

**Top 5 issues**
1. **High:** Claude's review loop can run without limit (one paid review per
   round) when a rejection's issues are not spelled exactly `"blocking"`.
2. **High:** `forge pending` re-runs the regression and commits a new branch
   with identical code on every 30-minute tick while Claude stays unavailable
   but the internet is up.
3. **High:** sandboxed code's `/out` is a host bind mount with no size limit
   while it runs. Reproduced unintentionally: about 30 GB in two minutes.
4. **Medium:** review verdicts are not validated. A string issue crashes the run
   with `AttributeError`.
5. **Medium:** the lab-dashboard controls are reachable via DNS rebinding, and
   the PIN can be brute-forced (4-digit PIN in 2.8 s).

**Top 3 recommended enhancements (all implemented)**
1. An `/out` watchdog that stops runaway output while the code runs.
2. Backoff for `forge pending`, plus a no-recommit guard.
3. A per-run Claude review budget (`[claude] max_cost_usd`).

## 4. Detailed High findings

### 1 — Claude's review loop has no bound

**Mechanism.** In `_execute`, `blocking = [i for i in verdict.get("issues", [])
if i.get("severity") == "blocking"]`. When Claude does not approve and no issue
is spelled exactly `blocking`, `code_issues` is empty, and
`if source == "claude" and not code_issues:` treats it as an image-only
rejection. `rerender_images(run, cfg, [])` returns `[]`, `only_images` becomes
`[]`, and `continue` starts another full Claude review. `code_rounds` is never
incremented, so `max_review_rounds` never applies.

**Failure scenario.** Any of these Claude replies:
- `{"approved": false, "issues": []}`
- `{"approved": false, "issues": [{"severity": "critical", ...}]}`
- `{"approved": false, "issues": [{"severity": "Blocking", ...}]}`

Each produces a paid review every round, until a human kills the process.

**Fix.**
- `normalize_verdict` lower-cases severities and maps blocking synonyms
  (`blocker`, `critical`, `high`, `major`, `severe`, `error`, `must fix`).
- It coerces `approved` to a strict bool, and turns string or `null` issues
  into dicts.
- When the verdict rejects without any blocking issue, it adds one unroutable
  blocking issue, so the rejection consumes a round.
- The image-only branch now also requires `blocking` to be non-empty.

### 2 — `forge pending` makes a duplicate branch every tick

**Mechanism.**
1. `cmd_pending` checks only that the *internet* probes answer, then
   `reopen` → `execute`.
2. `_execute` repeats the regression and output builds, and Claude fails
   again. Overload, 429, 5xx and "timed out" all count as transient.
3. `defer()` runs and the loop `break`s into the commit section.
4. `commit()` always creates a new uniquely-named branch.

**Failure scenario.** A multi-hour Claude overload, or a project whose review
always exceeds `[claude] timeout`, yields 2 identical branches an hour and
repeated sandbox and GPU work. `forge pending` reports success throughout.

**Fix.**
- The commit records `deferred_hash = module_hash(module)` when Claude's
  review is deferred.
- When a pending re-run finds Claude still unavailable and the module hash is
  unchanged, it restores `phase = committed` on the existing branch and returns
  without committing.
- `forge pending` then backs off (30 min, 1 h, 2 h, 4 h, then every 8 h;
  `[claude] pending_backoff_minutes`).
- `forge pending run RUN` forces a single run now.

### 3 — `/out` can fill the host disk

**Mechanism.** The output directory is bind-mounted read-write. Docker's
`--memory`, `--pids-limit` and the `/tmp` tmpfs size do not bound it, and the
only check (`copy_outputs`'s `max_bytes`) runs after the container exits.

**Failure scenario.** Generated `build_outputs` or capture code with a loop
that writes frames: within the 120 s default timeout (longer for toolchains)
it can write tens of GB to `runs/<run>/outputs.tmp`. A full disk then breaks
`atomic_write` of `state.json`, other services and the lab's git repo. During
this review, the new test run against the received code wrote about 30 GB in
two 60-second sandbox runs before the timeouts fired.

**Fix.**
- `_run_watched` runs the command with `Popen` and polls the folder size once
  a second (`os.scandir`, links not followed, stops counting at the limit).
- Over `[sandbox] out_watch_mb` it kills the process, `docker kill`s the
  container by name, empties `/out`, and returns
  `OUTPUT LIMIT: ...` as a failed run.
- The default is `max(4 × outputs_max_mb, 2048)` MB, so legitimate
  intermediate files in `/out` are not refused; `0` disables the watch.
- Runs without an `out_dir` still use `subprocess.run` unchanged.

**Migration and behaviour changes**
- No state or plan migration. New state keys (`deferred_hash`,
  `deferred_tries`, `deferred_retry_at`) are additive.
- A run deferred by the old version has no `deferred_hash`, so its first
  pending tick may commit once more; after that the guard applies.
- Severities "Blocking", "critical", "high" and "major" now block.
- `"approved"` must be `true` (or "true"/"yes"); other truthy values such as
  `1` no longer approve.
- A rejection naming no blocking issue now costs a round, then goes to Claude
  (self-review) or stops or auto-changes (Claude).
- Dashboard controls through a Host that is not an IP, a one-word name, a
  local suffix (`.local .lan .home .internal .home.arpa .localdomain
  .localhost`) or listed in `allowed_hosts` now get 403. `allowed_hosts = ["*"]`
  restores the old behaviour.
- Stale chunk folders are now named `<id>-stale-YYYYmmdd-HHMMSS` (were
  `HHMMSS`); nothing in the code parses that name.

## 7. Open questions

1. **Rejection with only minor issues.** `REVIEW_SYSTEM` says "Only blocking
   issues prevent commit", but the loop has always treated `approved: false`
   as a rejection. I kept it a rejection (fail closed, now bounded). Should it
   instead be an approval with notes?
2. **`high` and `major` mapping to blocking** may be stricter than you want for
   the local self-review. Easy to narrow in `BLOCKING_SEVERITIES`.
3. **Private files** (`## Private files`) are mounted into every sandbox run.
   Generated code can print them (diagnosis prompts, Claude) or write them into
   outputs (commit, push). The docstring promises forge never copies them;
   should outputs and logs be scanned for their content before commit or Claude?
4. **`out_watch_mb` default (≥ 2 GB).** Does any toolchain (FO4 or Blender
   packaging, Godot export) legitimately write more than that to `/out`?
5. **Dashboard hostnames.** Is the hub ever opened by a public-looking DNS name
   (split-horizon DNS)? Those need `allowed_hosts`.
6. **Shape server** (carried over from the earlier review): still
   unauthenticated, with client-controlled `steps` and `octree_resolution`.
   Intended for a fully trusted LAN?
